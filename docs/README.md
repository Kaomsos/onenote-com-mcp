# 项目文档治理

本目录是项目级文档的统一入口。新增或移动文档时，应先确定文档职责，再放入对应子目录；不要在多个目录维护内容重复但权威性不明的副本。

## 目录职责

| 目录 | 内容 | 维护要求 |
| --- | --- | --- |
| [`design/`](design/) | 当前有效的架构、对象模型、解析器和工具契约 | 实现或公开契约变化时同步更新。 |
| [`overview/`](overview/) | 调研、评估和阶段性总体报告 | 标明评估范围和时间，不替代当前设计文档。 |
| [`dev/`](dev/) | 开发、验证、排障和人工操作流程 | 流程必须明确自动化边界、权限和前置条件。 |
| [`lesson/`](lesson/) | 从真实实现、排障和人工验证中提炼的可复用工程经验 | 区分观察、推断和当前决策；链接 canonical 契约，不自行定义契约。 |
| [`blog/`](blog/) | 面向公开阅读的工程实践文章与草稿 | 保持问题背景、术语和事实来源清晰，不替代设计或开发流程文档。 |
| [`todo/`](todo/README.md) | 跨文件或尚未实施的项目级待办及其索引 | 遵循编号、状态、优先级和索引同步规则。 |
| [`product/`](product/) | 当前产品能力、非承诺与产品层决策 | 与实现细节分离；参数和响应契约仍链接到 `design/`。 |

面向 GitHub 用户与外部贡献者的对外公开文档位于仓库根的 [`docs-public/`](../docs-public/README.md)（中英平行树，英文为对外权威版本）。本目录（`docs/`）仍是当前架构、契约与流程的内部权威来源；公开文档只做摘要与导航并链接回这里，不得把契约细节复制成第二份权威。修改本目录中被公开文档链接的内容时，检查 `docs-public/` 摘要是否需要同步。

## 文档变更规则

1. 当前架构和契约以 `design/` 为准；Lesson、评估报告或 TODO 不得成为已实现行为的唯一说明。
2. 开发流程放入 `dev/`；带证据边界且可复用的经验放入 `lesson/`；尚未实施、需要跟踪的工作放入 `todo/`，不得使用散落的 `TODO_*.md` 文件。
3. 文档移动或改名必须在同一变更中更新仓库内全部相对链接。
4. 新增目录级文档时，应提供 `README.md` 作为该目录的入口或索引。
5. 代码、配置或工具契约变化后，应检查 `README.md`、`AGENTS.md` 和相关设计/开发文档是否需要同步。

## 开发与验证入口

- [Pytest Windows sandbox 临时产物隔离](dev/pytest_windows_sandbox_artifact_isolation.md)：默认自动测试在人工终端、Codex sandbox 与并发 session 之间的临时根、cache 和保留策略。
- [OneNote mutation 隔离验证流程](dev/isolated_mutation_validation.md)：只能由用户本人启动的真实后端验证边界与操作步骤。

## Lesson 治理

Lesson 的权威索引是 [`lesson/README.md`](lesson/README.md)。Lesson 必须说明观察时间与范围，明确区分真实观察、工程推断和当前设计决策，并链接到 `design/` 或 `dev/` 中的 canonical 内容。具体约束见 [`lesson/AGENTS.md`](lesson/AGENTS.md)。

## TODO 治理

TODO 的权威索引是 [`todo/README.md`](todo/README.md)。具体规则包括：

- 文件名使用不可变的三位数字前缀：`NNN_<short_slug>.md`；
- 每个文件显式记录 ID、状态和优先级；
- 新编号取当前最大编号加一，已完成或已取消的编号也不得复用；
- 新增、更新、完成或取消 TODO 时，必须同步修改索引；
- 完成后的 TODO 保留在原路径作为决策与验收记录，不重新编号。
